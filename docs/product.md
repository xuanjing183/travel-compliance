> 面向作品集 / HR 3 分钟演示与技术面 10 分钟深挖（U-01）。本文回答「这是什么产品、给谁用、
> 解决什么问题、边界在哪」。技术结构与实现决定见 [architecture.md](architecture.md)，
> 模型与外部集成见 [integration.md](integration.md)，接口契约见 [api.md](api.md)。

## 1. 业务问题

50～500 人的中小企业通常把差旅制度放在 Word、Markdown 或 PDF 里：

- **员工**靠自己翻制度，不知道「我这个级别去成都能住多少钱一晚」「要提前几天订机票」；
- **审批人**靠经验判断，超标与否口径不一，改一版制度就要重新培训；
- **财务**往往到**报销阶段**才发现超标，钱已经花出去了，只能事后追讨或认栽。

制度是「写给人看的散文」，而成本、档位、提前期这些判断其实是**可计算的规则**。问题是没人把
散文编译成规则，也没人在**花钱之前**（规划阶段）就用规则算一遍。

## 2. 产品主张

**把差旅制度编译成可确认、可执行、可追溯的规则，在规划阶段就算清成本、识别例外，把真正需要
人判断的事项交给直属经理审批，并完整保留从输入 → 条款 → 规则 → 供应商数据 → 审批 → 交付的
证据链。**

三个关键词：

| 关键词 | 含义 | 对应能力 |
|---|---|---|
| **可确认** | 模型从制度原文抽取的规则是**候选**，必须经管理员逐条确认（含引用定位）才能发布；模型不能直接决定标识与数值 | 制度编译 #19–#23（上传 → 抽取 → 审核 → 发布） |
| **可执行** | 已确认规则在规划时真实参与计算：城市档位、住宿/补贴上限、舱位、提前期、自动审批阈值 | 确定性规则核心 + 规划器（金额一律整数「分」，HC-02） |
| **可追溯** | 每个结论都能回到来源：方案里交通/酒店/天气/摘要各带 `source` 徽标，规则判断带条款引用，全程写不可变审计 | 来源标识（§6.1）+ 追加式审计（HC-11） |

## 4. 核心用户故事（12 个验收场景，S-01～S-12）

这 12 个场景既是产品故事，也是确定性验收场景（fake 模式 36/36 通过，AC-019）。完整判定见
契约 §7.2 与 [acceptance.md](acceptance.md)。

| 场景 | 用户故事 | 产品要点 |
|---|---|---|
| **S-01 黄金路径** | 张三说「下周去上海参加供应商大会，预算 4000」，系统补全 → 规划 → 超自动审批阈值 → 李四批准 → 交付 | 规划阶段算出总额 476000 分，识别 `BUDGET_EXCEEDED`/`OVER_AUTO_APPROVAL_LIMIT`，走人工审批 |
| **S-02 自动通过** | 合规且低于预算/阈值的短途出差 | `AUTO_APPROVED → DELIVERED`，无需人工，体现「只把该判断的交给人」 |
| **S-03 酒店超标** | 去成都，无协议酒店，只能订备用酒店 450 元/晚（员工 B 类上限 400） | 违规 `HOTEL_OVER_CAP`，标注超标金额与来源 `backup_fixture`，进审批而非硬阻断 |
| **S-04 提前不足** | 紧急会议，只提前 2 天订机票（制度要求 3 天） | `ADVANCE_BOOKING_VIOLATION`，软违规进审批 |
| **S-05 缺失信息** | 只说「下周去杭州」 | 识别 destination=杭州，**不**把「下周」猜成具体日期，一次只追问缺失项、不重复追问已知项 |
| **S-06 硬性阻断** | 出行日期已过（2026-10-19～20，今天 10-20） | `POLICY_BLOCKED`，**不调用**任何 Provider，审计记录阻断原因（省钱 + 可解释） |
| **S-07 驳回** | 李四驳回「预算过高，请改为线上参会」 | `REJECTED`，恰好 1 封 `workflow_notification`，无交付邮件；重复审批返回 409 |
| **S-08 要求修改** | 李四要求修改 → 张三改预算重提 → 再批准 | revision+1，旧审批卡作废（`superseded`）并审计，两次决定均可追溯 |
| **S-09 交通故障** | 交通 Provider 超时 | **不崩溃**：交通标「待人工补录」，`total_fen=null` 但给 `known_subtotal_fen`，绝不把缺失交通按 0 计入而误判自动通过 |
| **S-10 重启恢复** | 到 `PENDING_APPROVAL` 后杀掉进程，用同一数据库重启 | Trip/revision/审批待办不丢，从审批后节点恢复，只生成 1 封交付邮件（跨进程持久化 + 幂等） |
| **S-11 图片入口** | 上传会议邀请函图片 | 多模态抽取城市/日期/事由/地址，**确认前不改 Trip**，确认后写入并审计（抽取只是提议） |
| **S-12 制度变更** | S-01 待审批时发布 v1.3，点「按新版本重新校验」 | revision+1，绑定 v1.3，旧审批失效，480/晚超新上限 450 新增违规，审计保留 v1.2 与 v1.3 两次结果 |

## 5. 一次完整体验（黄金路径）

1. 员工在工作台用一句话发起差旅，系统抽取槽位并**只追问缺失项**；
2. 槽位齐了点**提交**：系统按已确认规则规划——选交通/酒店候选、算成本（整数分）、判违规；
3. 若合规且低于阈值 → **自动通过**并交付；否则 → 生成**审批卡**（含成本拆解、违规、条款引用、来源）进入 `PENDING_APPROVAL`；
4. 直属经理**批准 / 驳回 / 要求修改**（须填意见）；批准后写本地 Outbox 交付邮件；
5. 全程每个结论带**来源徽标**，时间线保留**不可变审计**；制度改版后可**重新校验**。

## 6. 范围与边界（诚实声明）

这是一个**本地可复现的演示项目**，刻意不连接真实世界：

- **不**连接真实订票 / 支付 / 邮件系统；交付终点是**本地 Outbox**（`GET /api/outbox` 可查）。
- 交通/酒店/天气来自**本地 Demo Provider fixture**（确定性、可故障注入）；真实 Live Provider 未授权（AUTH-02，标记 `blocked`）。
- 模型调用默认 **fake 模式**（零网络、确定性）；真实模型（DashScope）仅在 AUTH-01 授权下用于门控评测，且受费用守卫与出站网络边界约束。
- `X-Demo-User` 是演示身份切换，**不是认证/授权机制**；真实部署需替换为真正的身份系统。
- 金额一律整数「分」存储与计算（HC-02），界面显示时换算为元；模型只写摘要文字，**金额只来自代码计算**。

## 7. 价值小结

对**员工**：不用翻制度，规划阶段就知道合不合规、要花多少、为什么。
对**审批人**：拿到的是算好的成本拆解 + 违规 + 条款引用，判断有据，口径统一。
对**财务/公司**：超标在**花钱之前**被发现，而不是报销之后；制度改版可重新校验存量申请；全链路可审计。
