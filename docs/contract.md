## 1. 问题与目标

### 1.1 要解决的问题

50～500 人的中小企业，差旅制度通常写在 Word/PDF 里。员工提申请时靠自己翻制度，审批人靠经验判断是否超标，行政/财务往往事后报销时才发现违规。痛点是：

1. 员工不知道标准，方案反复被打回；
2. 审批人看不到“为什么超标、超了多少、依据哪条”；
3. 制度更新后，旧标准仍在被使用；
4. 出了问题无法追溯是谁、依据什么做的决定。

### 1.2 一句话定位

> 把企业差旅制度编译成可执行规则，让 Agent 在规则内规划行程，例外走人工审批，全过程可追溯。

### 1.3 用户

| 角色 | 演示账号 | 核心诉求 |
|---|---|---|
| 员工 | 张三（销售部，北京） | 快速提交合规方案，少被打回 |
| 审批人 | 李四（销售部经理，张三的直属上级） | 一眼看懂例外原因和成本，快速决策 |
| 管理员 | 王五（行政/财务） | 维护制度版本，确认规则，查审计 |

### 1.4 成功标准（产品层）

演示与评测中可量化展示：制度问答引用命中率、规则抽取召回率、场景端到端通过率、黄金路径耗时、每次审批的依据完整性。具体阈值见第 8 节。

## 3. 业务规则口径（消除歧义）

以下为演示公司“星衡科技”的制度数值。数值可由项目所有者修改（Q-03），修改不影响架构。

### 3.1 制度版本

| 版本 | 状态 | 与上版差异 |
|---|---|---|
| v1.0 | 已归档 | 机票需提前 5 天预订；自动通过阈值 2000 元 |
| v1.2 | 当前生效 | 机票提前 3 天；自动通过阈值 3000 元 |

每个行程在规划时绑定当时生效的制度版本。

### 3.2 规则（v1.2）

| 规则类型 | 内容 |
|---|---|
| 城市等级 | A：北京、上海、广州、深圳；B：杭州、南京、成都、武汉、西安、重庆、苏州、天津；C：其他 |
| 住宿上限（元/晚） | 员工 A500 / B400 / C300；经理及以上 A650 / B500 / C400 |
| 伙食补贴（元/天） | A100 / B80 / C60，按行程自然日数计 |
| 交通舱位 | 全员经济舱或高铁二等座 |
| 提前预订 | 机票出发日距申请日 ≥ 3 天 |
| 自动通过阈值 | 方案总额 ≤ 3000 元，且无违规、不超申报预算 |
| 单次时长 | 单次出差 ≤ 15 天；超出不在本系统处理 |

规则引擎只支持上述**封闭的规则类型集合**。抽取出的规则如果不属于这些类型，要标记为“不支持，需人工处理”，不能静默丢弃。

### 3.3 计算口径

- 晚数 = 结束日期 − 开始日期；天数 = 晚数 + 1。
- 方案总额 = 往返交通 + 酒店单价 × 晚数 + 伙食补贴 × 天数。景点、餐饮等行程活动费用不计入。
- 金额单位为人民币元，保留两位小数，统一由代码计算。
- “当前日期”由时钟 Provider 提供；Demo 模式固定为 `DEMO_TODAY=2026-10-20`，保证结果可复现。

### 3.4 必填信息

出发地、目的地、开始日期、结束日期、出差事由、申报预算。偏好和会议地址是可选项。缺什么只问什么，已识别的信息不要重复确认。

### 3.5 违规分级与审批判定

| 级别 | 示例 | 结果 |
|---|---|---|
| 硬性阻断 | 出发日早于当前日期、结束早于开始、超过 15 天 | `POLICY_BLOCKED`，员工修改后重新提交 |
| 可审批例外 | 酒店超上限、提前天数不足、总额超申报预算、关键 Provider 不可用导致方案不完整 | 进入审批 |
| 无违规 | — | 总额 ≤ 自动通过阈值时 `AUTO_APPROVED`，否则进入审批 |

审批人是员工的直属经理，只有一级审批；审批人不能是申请人本人。

审批决定有三种：

- `approve`：通过，进入交付；
- `reject`：驳回，必须填写意见，行程结束，并通知员工；
- `request_changes`：要求修改，必须填写意见；行程回到信息收集阶段，员工修改后重新规划，版本号 +1，旧方案保留在审计里。

如果待审批期间发布了新的制度版本，审批卡要提示“制度已更新”，并提供“按新版本重新校验”。

### 3.6 交付

审批通过或自动通过后，由工作流节点生成一封邮件写入 Outbox：

- 收件人：员工；
- 抄送：审批人（自动通过时作为知会）。

正文由模板根据结构化方案渲染。模型只能生成其中的一段摘要文字，不能改动金额、日期和航班信息。

## 4. 需求清单

优先级：**M** = 必须，**S** = 应当。全部纳入本次范围（C-03）。

### 4.1 需求接入

- **R-01 (M)** 员工用自然语言提交需求，系统抽取必填槽位，只追问缺失项。
- **R-02 (M)** 支持多轮补充和修改槽位；每次修改都记入审计。
- **R-03 (S)** 支持上传会议邀请图片（PNG/JPG），抽取城市、日期、事由，并由员工确认后填入。

### 4.2 制度知识与规则

- **R-04 (M)** 制度问答基于当前生效版本，答案必须附条款编号和原文引用；制度中没有的内容要明确说不知道。
- **R-05 (M)** 管理员上传制度文档（Markdown/PDF），系统生成草稿版本。
- **R-06 (M)** 系统从草稿中抽取候选规则。每条规则包含：类型、条件、数值、单位、来源条款编号、原文引用。原文引用必须能在文档中逐字找到，否则标记为无效。
- **R-07 (M)** 管理员逐条确认、修改或拒绝候选规则；只有全部规则处理完毕的版本才能发布。发布后旧版本归档。
- **R-08 (M)** 运行时合规校验只使用已发布版本中已确认的规则。

### 4.3 规则引擎与规划

- **R-09 (M)** 按第 3 节口径，由代码完成成本计算、违规识别和审批判定。每个违规项都要包含规则 ID、制度版本、条款原文、实际值和限额。
- **R-10 (M)** 航班专家根据路线和日期，从 Provider 获取候选航班，返回结构化候选。
- **R-11 (M)** 酒店专家优先从协议酒店库中选择，返回结构化候选；Live 模式可用联网搜索补充参考信息，但搜索结果不作为带价格的候选。
- **R-12 (M)** 行程专家根据事由、会议安排、天气和员工偏好，生成每日行程。
- **R-13 (M)** 最终选择由代码完成：在合规候选中按价格和偏好排序；没有合规候选时，选择最接近标准的一项，并标记为违规。
- **R-14 (S)** 保存员工偏好（如航空公司、座位、酒店品牌、早班机回避），并在规划中使用；员工可以查看和修改。

### 4.4 审批与交付

- **R-15 (M)** 需要审批时，工作流暂停，并为审批人生成审批卡：成本拆解、违规项及依据、申报预算对比、方案摘要。
- **R-16 (M)** 审批人可以批准、驳回或要求修改；服务端必须校验审批人身份。
- **R-17 (M)** 服务重启后，待审批的行程仍然存在，审批后能正确恢复执行。
- **R-18 (M)** 通过后按 3.6 写入 Outbox，并生成可查看的行程单。
- **R-19 (S)** 待审批期间如果制度发生变更，按 3.5 给出提示，并支持重新校验。

### 4.5 溯源、可靠性与工作台

- **R-20 (M)** 每个行程都有审计时间线，至少记录：槽位变更、检索到的条款、触发的规则、Provider 调用及数据来源、方案版本、审批决定、邮件写入。
- **R-21 (M)** 所有外部依赖都通过 Provider 接口访问，分 Demo / Live 两种实现，通过配置切换。Demo 模式下，除模型 API 外不访问任何外部服务。
- **R-22 (M)** 管理员可以注入故障：航班超时、无协议酒店、天气不可用。系统要按第 6.5 节定义降级，不能崩溃。
- **R-23 (M)** 三角色工作台：员工（对话、方案、引用、进度、偏好）；审批人（待办、审批卡）；管理员（制度版本、规则审核、Provider 健康状态、故障注入、审计、Outbox）。
- **R-24 (M)** 界面和数据中要标明信息来源（`demo_fixture` / `live` / `policy`）。
- **R-25 (M)** 提供一键重置演示数据。

### 4.6 评测与文档

- **R-26 (M)** 制度问答评测集，至少 25 题，其中至少 5 题是制度中无答案的。
- **R-27 (M)** 规则抽取评测：拿 v1.2 文档的抽取结果，对比标准规则集。
- **R-28 (M)** 端到端场景评测：见第 7 节的 12 个场景。
- **R-29 (S)** 检索方案对比：纯向量检索 vs 混合检索（BM25 + RRF）。只有指标更好才保留混合检索，并记录结论。
- **R-30 (M)** 文档：README（第一段写业务问题，技术栈放最后）、`product.md`、`architecture.md`（含取舍说明）、`integration.md`（如何对接客户已有的 OA/HR/邮件系统）、`api.md`、`demo-script.md`（3 分钟版和 10 分钟版）、`acceptance.md`。

## 5. 硬约束（不可让步）

- **HC-01** 金额、日期、晚数、阈值、合规与审批判定只能由代码计算。模型输出不能直接作为合规结论。
- **HC-02** 违规项必须能追溯到“已发布版本中已确认的规则”和条款原文。
- **HC-03** 航班、酒店的价格和班次只能来自 Provider 的返回结果，模型不能编造。代码要校验每个候选 ID 都在 Provider 返回结果中。
- **HC-04** 写 Outbox 只能发生在 `APPROVED` 或 `AUTO_APPROVED` 之后，由工作流节点执行。不能作为工具暴露给自由决策的 Agent。
- **HC-05** 审批操作由服务端校验身份：只有该行程的直属经理可以审批，申请人不能审批自己的行程。
- **HC-06** Demo 模式下，除模型 API 外不访问外部网络。
- **HC-07** 仓库不提交任何密钥，只提供 `.env.example`；日志不能输出密钥。
- **HC-08** 素材目录只读。
- **HC-09** Mock / fixture 数据必须明确标注来源。不能用 Mock 结果宣称真实集成已经通过。

## 6. 共享契约

本节是前端、后端、工作流、评测共同依赖的接口。在 M1 结束前冻结到 `docs/api.md`。

路径命名和字段的具体写法属于 A 类，可以调整；但语义变更属于 C 类，需要修订契约。

### 6.1 行程状态机

```text
COLLECTING ──(槽位齐全)──▶ PLANNING ──▶ 规则校验
   ▲                                    ├─ 硬性阻断 ─▶ POLICY_BLOCKED ─(员工修改)─▶ COLLECTING
   │                                    ├─ 自动通过 ─▶ AUTO_APPROVED ─▶ DELIVERED
   │                                    └─ 需审批   ─▶ PENDING_APPROVAL
   │                                                   ├─ approve ─▶ APPROVED ─▶ DELIVERED
   │                                                   ├─ reject  ─▶ REJECTED（终态）
   └──────────────── request_changes ◀─────────────────┘   （revision + 1）
```

`DELIVERED` 和 `REJECTED` 是终态。终态的行程仍然可以继续进行制度问答，但不能再修改方案。

### 6.2 核心实体（字段为最小集合）

| 实体 | 关键字段 |
|---|---|
| Employee | id, name, role（employee / manager / admin）, department, manager_id, home_city, preferences |
| PolicyVersion | version, status（draft / published / archived）, effective_date, document_path |
| PolicyRule | id, version, type, condition, value, unit, clause, quote, status（candidate / confirmed / rejected / unsupported）, confirmed_by |
| Trip | id, employee_id, status, revision, slots, policy_version, plan, cost_breakdown, violations, thread_id |
| Approval | trip_id, revision, approver_id, decision, comment, decided_at |
| AuditEvent | trip_id, ts, actor, type, payload, refs（rule_id / clause / provider / source）, trace_id |
| OutboxEmail | trip_id, to, cc, subject, body, created_at |
| ContractHotel | id, city, name, price, rating, distance_note, valid_until |

### 6.3 API（语义）

| 能力 | 方法与路径（暂定） |
|---|---|
| 演示账号 | `GET /api/users`；请求头 `X-Demo-User` 标识当前用户 |
| 行程 | `POST /api/trips`；`GET /api/trips`；`GET /api/trips/{id}` |
| 对话（驱动工作流） | `POST /api/trips/{id}/messages` → SSE |
| 图片上传 | `POST /api/uploads` |
| 审批 | `GET /api/approvals?status=pending`；`POST /api/trips/{id}/decision` |
| 审计 | `GET /api/trips/{id}/audit` |
| 制度问答 | `POST /api/policy/ask` |
| 制度管理 | `GET/POST /api/policies`；`POST /api/policies/{ver}/extract`；`GET/PATCH /api/policies/{ver}/rules`；`POST /api/policies/{ver}/publish` |
| 偏好 | `GET/PUT /api/users/{id}/preferences` |
| Outbox | `GET /api/outbox` |
| 演示控制 | `POST /api/demo/reset`；`POST /api/demo/faults`；`GET /api/health/providers` |

### 6.4 SSE 事件类型

`token`（模型流式文本）、`status`（节点进度）、`slots`（槽位更新）、`citation`（条款引用）、`plan`（结构化方案）、`violations`、`approval_required`、`trip_status`（状态变更）、`error`、`done`。

### 6.5 Provider 接口与降级

| Provider | Demo 实现 | Live 实现 | 故障时的行为 |
|---|---|---|---|
| Flight | 本地 fixture | Kiwi MCP | 航班部分标记为“待人工补充”，方案标记为不完整，必须进入审批，不能自动通过 |

| Weather | 本地 fixture | Open-Meteo | 省略天气信息，并在方案中注明，不阻断流程 |
| Clock | `DEMO_TODAY` | 系统时间 | — |
| Email | Outbox | Outbox | — |
